# 模块化方案生成系统（第一阶段）

## 目标

把病例截图和检测 PDF 转成可审核的结构化内容，再由 PPT 排版层消费已确认结果。模块定义、触发条件、提示词、输出结构和审核状态彼此独立。

## 目录

- `src/schemas/case-schema.mjs`：病例、指标、模块输出的字段契约。
- `src/modules/module-registry.mjs`：章节模块清单、输入字段、触发类型、提示词文件和版式标识。
- `prompts/case/`：截图病例事实提取提示词。
- `prompts/evidence/`：指标举证提示词。
- `prompts/modules/`：每个 PPT 章节独立的提示词文件。
- `prompts/shared/`：所有模块共用的安全规则。

## 模块状态

- `not_applicable`：不符合触发条件，不生成。
- `missing_data`：触发了，但必需资料缺失，不能生成个体化内容。
- `draft`：已生成，等待人工审核。
- `confirmed`：人工确认，可以进入 PPT。
- `excluded`：人工排除，不进入 PPT。

审核字段统一使用：`待审核`、`已确认`、`已修改`、`已排除`、`待补充`。

## 触发原则

1. `always`：封面、致客户说明、最后寄语等基础章节。
2. `report`：存在对应类型的已确认报告或指标时触发。
3. `food-related`：有食物检测结果或真实食物反应史时触发。
4. `depends-on`：上游章节已经生成后才触发，例如替代方案依赖饮食回避。
5. `missing_data`：模块触发但缺少个体化所需字段时，返回待补充，不使用猜测值。

## 第一阶段边界

这一阶段只建立契约和注册表，不改变现有 PPT 排版、不替换旧建议接口、不自动将模块草稿送入 PPT。下一阶段再把 `SUGGESTION_RULES` 迁移到该注册表，并接入模块级生成和审核。

## API

- `GET /api/modules`：返回当前模块注册表，供前端显示章节、触发条件、提示词文件和版式标识。
